## 1. Где лежат утренние сценарии и вечерняя рутина

### v1 (корень репозитория)

Облако: таблица `public.lifeos_docs` (одна таблица документов на пользователя).

| Колонка | Тип | Смысл |
|---|---|---|
| `user_id` | uuid | владелец, по умолчанию `auth.uid()`, часть первичного ключа |
| `id` | text | id документа, часть первичного ключа |
| `data` | jsonb | сам документ |
| `updated_at` | timestamptz | время записи |

Доступ закрыт RLS: строка видна только своему `user_id`. Бот должен либо входить как этот пользователь, либо ходить с серверным ключом (ключ хранить в окружении бота, не в репозитории).

Документ **`id = 'os'`** — всё состояние v1 одним JSON (то же, что в `localStorage["lifeos.v1"]`). Запись целиком (`upsert`), поле `updatedAt` (мс, число) растёт при каждом сохранении; по нему приложение решает, чьи данные новее.

Нужные поля внутри `data`:

| Поле | Что это |
|---|---|
| `mScen` | **определения утренних сценариев**, массив из 3: `fast` («⚡ Быстро»), `home` («🏠 Дома»), `custom` («✏️ Кастом») |
| `mScen[].items[]` | пункты: `{id, name, min, note}` (порядок массива = порядок выполнения) |
| `mScenCur` | id сценария, который применён **сегодня** (`null`, пока не выбран или после правки) |
| `routines.morning[]` | **сегодняшний список утра**: копия пунктов применённого сценария + состояние: `{id, name, min, note, done, spent}` |
| `routines.evening[]` | вечерняя рутина (одна, без версий): те же поля |
| `day` | `{closedAt, evening}` — отметки закрытия дня и запуска вечера |
| `updatedAt` | мс, версия документа |

Пример (сокращён):

```json
{
  "v": 1,
  "updatedAt": 1795800000000,
  "mScen": [
    {"id": "fast", "name": "Быстро", "icon": "⚡", "items": [
      {"id": "a1", "name": "Раздуплиться ☕", "min": 3, "note": ""},
      {"id": "a2", "name": "Душ 🚿", "min": 10, "note": ""},
      {"id": "a3", "name": "Почистить зубы 🪥", "min": 0, "note": ""}
    ]},
    {"id": "home", "name": "Дома", "icon": "🏠", "items": [ ... ]},
    {"id": "custom", "name": "Кастом", "icon": "✏️", "items": [ ... ]}
  ],
  "mScenCur": "fast",
  "routines": {
    "morning": [{"id": "a1", "name": "Раздуплиться ☕", "min": 3, "note": "", "done": true, "spent": 190000}],
    "evening": [{"id": "e1", "name": "Записать дела на завтра 📅", "min": 10, "note": "", "done": false, "spent": 0}]
  },
  "day": {"closedAt": null, "evening": null}
}
```

Для бота «утренний сценарий на сегодня» = `mScen[id = mScenCur]`, а если `mScenCur` пуст — сценарий по дню недели (п. 4).
`routines.morning` — это уже применённый сегодняшний список со статусами; `mScen` — шаблоны.

Остальное в `data` бота не касается (задачи, проекты, привычки, журнал и т. д.). Другие документы в той же таблице: `map-<id>` — элементы карты желаний (картинки, тексты); к утру отношения не имеют.

### Beta (`v2/index.html`)

Только `localStorage` браузера, ключи `lifeos.v2`, `lifeos.v2.ui`, `lifeos.v2.fold` и т. п. При первом запуске копирует данные из `lifeos.v1`. В облако не пишет и из облака не читает. Для бота не источник.

### Beta 2.0 (`v2b/`, исходники `v2b/src/`)

Только `localStorage`, ключ `lifeos.v2b` (плюс служебные `lifeos.v2b.*`). При первом запуске копирует данные из беты, дальше живёт самостоятельно. Облака нет (карта желаний ходит в локальный IndexedDB `lifeos-map`; облачный код для неё в v2b отключён).

Модель сценариев в Beta 2.0 (внутри `S` в `lifeos.v2b`):

- `S.scen[]` — сценарии: `{id, kind: "morning" | "evening" | "custom", name, icon, versions[]}`; `versions[]` — `{id, name}`. Для утра версии те же, что в v1: `fast`, `home`, `custom` (id сохранены при переносе).
- **Пункты сценария — обычные задачи** в `S.tasks` с `type: "сценарий"`, `sc` — id сценария, `sv` — id версии, `name`, `min`, `check[]` (чек-лист `{text, done}`), `desc`, `ord`; подзадачи «до/после» — задачи с `link` (id родителя) и `rel: "pre" | "post"`.
- Сегодняшнее утро и вечер — задачи `type: "дела"` с `routine: "morning" | "evening"`, `done`, `doneAt`, `spent`, `tm` (таймер). Применённая версия сегодня: `S.day.scen.morning` = id версии.
- Фаза дня: `S.day.phase` = `morning | day | evening | closed`, день `S.day.iso` (ГГГГ-ММ-ДД).

## 2. Что синхронизируется с Supabase

| Что | Где живёт | В облаке? |
|---|---|---|
| v1: всё состояние (`mScen`, `routines`, задачи…) | документ `os` | да, сразу при каждом сохранении, realtime включён |
| v1: карта желаний | документы `map-<id>` | да |
| v1: таймер, вид (`lifeos.timer.v1`, `lifeos.view.v1`) | `localStorage` | нет |
| Beta (`lifeos.v2*`) | `localStorage` | нет |
| Beta 2.0 (`lifeos.v2b*`), в т. ч. сценарии, утро/вечер, `S.day` | `localStorage` | нет |
| Карта желаний в Beta 2.0 | IndexedDB `lifeos-map`, на каждом устройстве свой | нет |

Важно: данные Beta 2.0 **расходятся с v1** с момента копирования. Если Дмитрий правит сценарии в Beta 2.0, бот, читающий `os`, этих правок не увидит.

## 3. Какую версию считать главной и план облака для Beta 2.0

**Сейчас главной для бота считать v1 (документ `os`)** — это единственное облако. Разработка идёт в Beta 2.0, и Дмитрий переедет на неё. Чтобы бот не ломался при переезде, предлагаю не завязывать его на внутреннюю структуру ни v1, ни Beta 2.0, а договориться о **маленьком отдельном документе-«витрине»**.

### Документ `bot-morning` (пишет приложение, читает бот)

Отдельная строка в `lifeos_docs`, `id = 'bot-morning'`. Формат версионирован полем `schema`, поля только добавляются, существующие не переименовываются и не меняют смысл.

```json
{
  "schema": 1,
  "updatedAt": 1795800000000,
  "tz": "Asia/Ho_Chi_Minh",
  "dayStartsAt": "04:00",
  "defaults": { "morning": { "1": "fast", "2": "home", "3": "fast", "4": "home", "5": "fast", "6": "home", "0": "home" } },
  "morning": {
    "versions": [
      {"id": "fast", "name": "Быстро", "icon": "⚡", "items": [
        {"id": "a2", "name": "Душ 🚿", "min": 10}
      ]}
    ],
    "today": {"day": "2026-11-27", "versionId": "fast"}
  },
  "evening": { "items": [ {"id": "e1", "name": "Записать дела на завтра 📅", "min": 10} ] }
}
```

- Ключи `defaults` — дни недели по `Date.getDay()` (0 = воскресенье, 1 = понедельник).
- `items[].id` стабильны между правками (нужны боту для отметок, п. 5). `min = 0` — см. п. 4.
- Приложение (v1 и затем Beta 2.0) обновляет документ при любом изменении сценариев и при смене дня. Бот только читает.

### Этапы

1. **Сейчас, без изменений в приложении:** бот читает `os` → `mScen`, `mScenCur`, `routines`. Это работает уже сегодня.
2. **v1 + витрина (маленькая правка):** v1 пишет `bot-morning` из `mScen`/`routines.evening`. Бот переключается на витрину.
3. **Облако для Beta 2.0:** подключить тот же шим Supabase, что в v1, но писать в **отдельный** документ `os2` (не в `os`, чтобы не перезаписать v1). Beta 2.0 тоже пишет `bot-morning`. Когда Дмитрий окончательно переедет, `bot-morning` остаётся единым контрактом, а бот ничего не меняет.
4. Даты не обещаю: этап 3 ещё не запланирован, Дмитрий решает, когда.

## 4. Выбор сценария по дню недели и `min = 0`

**Выбор утреннего сценария** (v1 и Beta 2.0 одинаково): понедельник, среда, пятница → `fast` («Быстро»); остальные дни (вт, чт, сб, вс) → `home` («Дома»). `custom` не выбирается автоматически, только вручную. В v1 утром показывается выбор из трёх сценариев; если Дмитрий не выбрал, через 5 минут запускается сценарий по дню недели. В Beta 2.0 по тому же правилу подсвечивается версия по умолчанию (★), применяется по кнопке.

**Новый день начинается в 04:00** по местному времени (до 04:00 ещё «вчера»), часовой пояс Дмитрия сейчас Asia/Ho_Chi_Minh (UTC+7). Отметки «сделано» у утра и вечера сбрасываются при смене дня. Для расчёта «сегодняшней даты» бот должен брать `now − 4 часа`.

**`min = 0`** — у пункта нет оценки времени. Следствия: в приложении он идёт секундомером (считает вверх, а не вниз), в сумме минут сценария учитывается как 0, автозапуск следующего пункта таймером его не стартует сам, подпись «N мин» не показывается. Пример: «Почистить зубы 🪥», «Одеться 👕». Для бота: показывать без длительности и не считать в сумме.

## 5. Может ли бот записывать отметки о выполнении

Да, но **не в тот же документ, который пишет приложение**. И v1 (`os`), и Beta 2.0 перезаписывают документ целиком, а выигрывает последняя запись: если бот допишет `done` внутрь `os`, следующее сохранение приложения затрёт отметку или, хуже, бот затрёт правки приложения.

Предлагаю схему «один писатель на документ»:

- Бот пишет только в **свой** документ `bot-checkins` (`id = 'bot-checkins'`), приложение его не пишет, только читает.
- Формат: журнал событий по дням, только добавление.

```json
{
  "schema": 1,
  "days": {
    "2026-11-27": [
      {"item": "a2", "kind": "morning", "done": true, "at": 1795790000000, "by": "bot"}
    ]
  }
}
```

- Идемпотентность: событие определяется `(день, item, kind)`; повтор нажатия не создаёт дубль, а обновляет `done`/`at`.
- Приложение при загрузке и по realtime (таблица уже в публикации `supabase_realtime`) читает `bot-checkins` и применяет события за **сегодняшний день**: если `at` позже собственной отметки пункта — берёт отметку бота; иначе оставляет свою. Победитель выбирается по пункту, а не по документу, поэтому конфликтов целых документов нет.
- Старые дни (раньше 7 дней) бот обрезает, чтобы документ не рос.
- Приложение остаётся источником истины по структуре дня (фазы, закрытие дня, время по таймеру); бот влияет только на `done` у пунктов.
- Пока приложение не умеет читать `bot-checkins`, бот должен только **читать** и показывать состояние, а отметки не писать. Это отдельная небольшая правка приложения (v1 и/или Beta 2.0), её нужно согласовать с Дмитрием.
